Web media interoperability

The same video, seconds out of sync — depending on your browser

Inside a video file there can be a tiny instruction that says “hold the picture back a moment so it lines up with the sound.” Some browsers follow it. Some ignore it. And the surprising part: the same browser can do both, depending on how the video is loaded.

TL;DR — Two self-contained demos (about 12 KB each) let you see and hear the problem in your own browser, then switch browsers to watch the result flip. Below them: why it happens, and how it got fixed across Chrome, Safari, Firefox and the specification.

What’s actually going on

A video file can carry an edit list — a small note to the player. Ours says “delay the picture by 3 seconds”, so that the picture and a separately-timed soundtrack end up aligned. Nothing exotic; it’s a standard part of the MP4 format that editing tools emit all the time.

To make the effect impossible to miss, the test file has a white flash in the picture and a beep in the sound, positioned so they coincide only if the 3-second delay is applied:

Everything else is identical — the same bytes in every browser. The only thing that changes the outcome is the browser, and how it loads the video.

*The streaming row for Safari reflects WebKit trunk. A shipping stable Safari still shows the old “drops” result until the fix rides into a release — so if you test the streaming demo on today’s Safari, expect the picture 3 s early for now. Chrome likewise still drops it today; its fix is in progress (below).

Chrome and Firefox are mirror images, and — before the fixes — neither handled the same file the same way in both modes. There was no single “broken browser” to point at, because there was no agreed, written-down answer for what should happen. That’s what turned a bug report into an interoperability question: not “who’s wrong,” but “what’s the correct behaviour, and can everyone converge on it.”

Why it matters

This is one concrete way a live or on-demand video stream can silently drift out of lip-sync in the browser — invisible in ordinary content, and only pin-pointable with a file engineered to expose it. Reducing a real-world 2–3 second desync down to these two 12 KB pages is what made it possible to file precisely, in the same terms, against every engine and the spec at once.

How it got fixed

Filed as an interoperability clarification — observation, evidence, question — rather than an accusation. The engines and the standard are converging:

  • Safari · WebKit Changed to follow the delay under streaming. fixed →
  • Chrome Media team took the issue and is adapting, now that the others agree. in progress →
  • Firefox Already follows it under streaming (the common case); the plain-file side is filed separately. tracked →
  • The spec · W3C Byte-stream registry being clarified, so there’s finally one agreed answer. discussion →
  • Root cause, upstream The streaming server was patched to stop emitting the ambiguous edit in the first place. merged →
