Chromium MSE ignores a track's edit list (edts/elst)

The same media is played two ways in this browser. The video track carries a 1.0 s empty edit (a leading elst segment) that delays the picture by 1.0 s; the audio track has no such edit. A white flash sits at video media-time 0 and a 1 kHz beep at audio media-time 1.0 s, so flash and beep coincide only if the edit list is applied.

  • Left, MSE. The DASH init + media segments produced by ffmpeg -f dash are fed through MediaSource / SourceBuffer.appendBuffer (two source buffers, video + audio). The video init segment contains the elst.
  • Right, direct. The identical media as a progressive file via video.src.

Expected (per the MSE byte-stream spec, which requires edit lists to be honored): the MSE player shows the flash at presentation time 1.0 s, in sync with the beep, with video buffered.start = 1.0 s and duration = 5.0 s. Observed in Chromium: the MSE player drops the empty edit, so buffered.start = 0, duration = 4.0 s, flash painted at 0.0 s, 1.0 s ahead of the beep. Firefox honors it through MSE (this page shows the MSE player in sync there). The direct video.src player is included as a control that the media itself is correct.
